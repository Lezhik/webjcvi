This file is append-only. Each iteration adds a new section; earlier entries are never edited or deleted.

## Preparation — project bootstrap

**Date:** 2026-09-11

**Decision.** Stand up the dual-surface skeleton required by `docs/tz.md` before the iteration loop begins: sandboxed file storage, a fixed-API DNA reader/report builder, a WebFlux+JTE web UI, an MCP tool surface on the same classes, and the automated tests in §5.4. The DNA decoder step (TZ §5.3) regenerates `build/reports/` from `jcvi-dna.txt` plus a codebase snapshot.

**Why this shape.**
- All file I/O is confined to `FileStorageService` (project-root sandbox, symlink-aware, 500 MB limit on read and write, DNA file treated as read-only). No other production class uses `java.nio.file.Files` or `FileInputStream`/`FileOutputStream`; ArchUnit enforces that.
- `DnaReportService.regenerate()` is the stable API for report lifecycle (clear prior reports, parse DNA, write markdown). Report *content* is intentionally a first cut: composition tables, IUPAC/invalid handling notes, a source-file snapshot, and growth notes. Later iterations may change the markdown without changing the method signatures.
- Ambiguous IUPAC characters are kept in the normalized sequence and counted separately; any other non-whitespace character is dropped from the sequence and counted as invalid so parsing never crashes (TZ §4.1).
- Both surfaces call the same services. Web: HTML pages plus `/api/files` and `/api/report`. MCP: `regenerate_dna_report`, `read_dna_report`, `list_files`, `read_file`.
- Blocking filesystem work on the web side is offloaded to `Schedulers.boundedElastic()`.

**MCP library.** `org.springframework.ai:spring-ai-starter-mcp-server-webflux:1.1.2` (SSE over WebFlux, Spring Boot 3.5 compatible). Tools are registered with `MethodToolCallbackProvider` from `@Tool` methods on `WebJcviMcpTools`. Spring AI 2.x was skipped because it requires Spring Boot 4 and would conflict with JTE's Boot 3 starter.

**Stack pins.** Java 21 bytecode, Spring Boot 3.5.15, Spring WebFlux, JTE 3.2.4 (`jte-spring-boot-starter-3`), Gradle Kotlin DSL, single module. No database.

**Tests.** Sandbox/size-limit coverage on `FileStorageService`, on the HTTP API, and on the MCP tool class; DNA parser edge cases; report regeneration clearing prior output; ArchUnit bypass checks. The 500 MB boundary is exercised through an injected smaller limit that uses the same comparison, plus an assertion that the production constant is `500L * 1024 * 1024`.

**Module split.** Not applicable — this is the initial single-module layout (TZ §6.8).

**DNA decoder.** After the test suite, `./gradlew generateDnaReport` (class `GenerateReportMain`) deletes `build/reports/dna/` contents and writes a fresh `build/reports/dna/dna-report.md`. DNA reports live under `build/reports/dna/` so regeneration does not wipe Gradle's own `build/reports/tests`. Generated reports stay git-ignored via `build/`.

## Iteration #1
- **Hypothesis:** The DNA encodes a *working-tape protocol* for arbitrary text, not a spec for DNA analysis and not a spec for this repository. Concrete signals from the v1 composition report: (R1) 0 ambiguous and 0 invalid bases — identity is fold-then-exact; (R2) A=199831 ≈ T=203352 (|A−T|=3521 of 531490) — one linear complementary buffer, not a graph; (R3) the 80-base preview contains poly-T (`TTTTT`) and poly-A (`AAAAA`) — consecutive identical symbols are a native delimiter; (R4) 7593 wrapped source lines — hits carry a line offset. Therefore the useful system is an in-memory **scratch tape**: a caller pastes any document, then exact-finds a motif and lists character runs. Payload is caller text; the DNA is only the protocol.
- **Functionality changes:** Shared class `ScratchTape` (no `FileStorageService`, no `jcvi-dna.txt`). Web: `/tape` load/find/runs UI; `POST /api/tape`, `GET /api/tape/find`, `GET /api/tape/runs`. MCP: `tape_load`, `tape_find`, `tape_runs`. Both surfaces.
- **Pros:** R1 and R4 map cleanly onto grep-like search of a pasted buffer, which agents actually need (search a log or draft without writing a project file). R3 maps onto run listing. The capability is independent of DNA content and of repo paths.
- **Cons:** Chargaff pairing (R2) is used only as “stay linear,” which is weak — A≈T is not really exercised by find/runs. Run structure was inferred from an 80-base preview, not measured on the whole tape. A paste-grep is useful but thin; it does not yet explain GC rarity or AT-richness beyond “keep the bound small” (524288 ≈ sequence length).
- **Report builder changes:** Replaced the bag-of-bases-only builder with wrap-frame census (min/median/mode/max line width of the raw FASTA wrapping) plus a whole-tape homopolymer profile (max run per base; buckets 5–9 / 10–19 / 20+). This addresses the cons: the next iteration sees measured runs and frame size instead of eyeballing the preview, so a stronger hypothesis can use those numbers rather than restating “the tape is linear.”

## Iteration #2
- **Hypothesis:** The DNA encodes a *record-separator protocol* for arbitrary text streams, not a grep tape and not DNA analysis. Concrete signals from the v2 wrap+homopolymer report: (R1) 8114 runs of length ≥ 5 but only 9 of length 10–19 and 1 of length 20+ — long homopolymers are rare banners, short ones are payload noise; (R2) longest A×22 and T×18, while G and C max out at 7 — the separator class is the abundant AT alphabet, never GC; (R3) wrap modal/median/max width 70 — frames are almost uniform. Therefore the useful system is a **banner splitter**: the caller pastes a log, email, or dump, and the app cuts it into sections on unusually long identical-character runs (`==========`, `----------`, `AAAAAAAAAA`). Default min-run 10 is the measured rare class. Payload is caller text; the DNA is only the delimiter rule.
- **Functionality changes:** Shared class `BannerSplitter` (no `FileStorageService`, no `jcvi-dna.txt`). Web: `/split` form UI; `POST /api/split`. MCP: `split_banners`. Both surfaces. Scratch tape from iteration #1 is kept (small step; this iteration adds sectioning rather than replacing search).
- **Pros:** R1 maps onto a real agent need: cutting pasted logs and email dumps on banner lines without writing a project file. Default 10 is taken from the measured 10+ rarity, not from the 80-base preview. The capability is independent of DNA content and of repo paths.
- **Cons:** Chargaff pairing is still not exercised by the splitter — A≈T only loosely justifies “use the abundant class as delimiters.” GC’s max run of 7 is noted but the splitter treats any long run (`====`) as a banner, not only AT. Wrap width 70 is unused by the product (only by the next report builder). A banner cut is useful but still a thin protocol; it does not yet use local pairing inside sections.
- **Report builder changes:** Replaced the wrap-histogram + homopolymer-bucket lead with **frame-window Chargaff skew**: walk the normalized tape in windows of modal wrap width, report mean/max |AT-skew| and |GC-skew|, and count windows whose |AT-skew| exceeds 0.05 (above the global residual ~0.009). Wrap census shrinks to “window source”; homopolymers shrink to a remainder line. This is a different reading (local pairing along frames) so the next hypothesis can use failing windows rather than restating “long runs are delimiters.”

## Iteration #3
- **Hypothesis:** The DNA encodes a *local pair-drift protocol* for arbitrary text, not a grep tape and not a banner splitter. Concrete signals from the v3 frame-window Chargaff report: (R1) global A=199831 ≈ T=203352 (|A−T|=3521, residual ~0.009) while **6108 of 7593** 70-base windows have |AT-skew| > 0.05 (mean 0.1515, max 0.7308) — pairing is an accounting identity, the payload is the drifted frames; (R2) window size is the modal wrap **70**; (R3) G↔C is the rarer complementary class and is even more locally skewed (mean |GC-skew| 0.257). Therefore the useful system is a **pair-drift scanner**: the caller pastes code, JSON, or a log, the app walks it in 70-char frames, and lists windows where complementary brackets `()[]{}<>` locally unbalance even when the whole paste still sums to ~zero leftover. Default threshold 0.05 is the measured local-failure floor. Payload is caller text; the DNA is only the pairing-vs-window rule.
- **Functionality changes:** Shared class `PairDrift` (no `FileStorageService`, no `jcvi-dna.txt`). Web: `/drift` form UI; `POST /api/drift`. MCP: `pair_drift`. Both surfaces. Scratch tape and banner splitter from #1–#2 are kept.
- **Pros:** R1 maps onto a real agent need: finding locally unmatched brackets in a pasted dump without writing a project file, including cases that globally still “balance.” Window 70 and threshold 0.05 are taken from the v3 census, not invented. The capability is independent of DNA content and of repo paths.
- **Cons:** Mapping A↔T onto `()`/`[]`/`{}`/`<>` is analogical, not literal — the DNA has no brackets. 80% of DNA windows fail, so “hotspot” in DNA is the majority class, while in code a hotspot is the bug; the polarity of the signal is stretched. Wrap joints and island geography were unused by the product (they become the next report). A windowed bracket tally is useful but still a thin protocol; it does not nest-match or report *which* pair class drifted.
- **Report builder changes:** Replaced the per-window mean/max skew table with **skew-island geography** (consecutive fail/pass windows compressed into islands: count, longest fail, longest pass) plus a **wrap-joint dinucleotide census** (last base of line N glued to first of line N+1; complementary AT/TA/GC/CG share; top dimers). Aggregate Chargaff and homopolymers shrink to a remainder line. This is a different reading (geography of drift + glue between frames) so the next hypothesis can use clustering and boundary dimers rather than restating “local pairing fails.”

## Iteration #4
- **Hypothesis:** The DNA encodes a *hard-wrap continuation protocol* for arbitrary text, not a grep tape, not a banner splitter, and not a bracket-drift scanner. Concrete signals from the v4 island+joint report: (R1) wrap min/median/modal/max = 50/70/70/70 — almost every line is a full frame of 70; (R2) wrap joints are **26.6% complementary** (below independent ATGC chance ~32%) and the top dimers are same-base **TT×1295** and **AA×1244**, so the glue continues the linear tape rather than closing a pair; (R3) fail islands run as long as 44 windows while pass islands max out at 5 — long wrapped regions are the payload, a short line is the break. Therefore the useful system is an **unwrapper**: the caller pastes hard-wrapped email, changelog, or man-page text, and the app joins lines of length ≥ 70 into paragraphs, ending a paragraph on a shorter line. Default width 70 is the measured modal wrap. Payload is caller text; the DNA is only the wrap-as-display rule.
- **Functionality changes:** Shared class `WrapReflow` (no `FileStorageService`, no `jcvi-dna.txt`). Web: `/reflow` form UI; `POST /api/reflow`. MCP: `unwrap_wraps`. Both surfaces. Tape, banner split, and pair-drift from #1–#3 are kept.
- **Pros:** R1+R3 map onto a real agent need: reconstructing paragraphs from 70-column wraps without writing a project file. The stitch-vs-break rule is taken from measured line widths, not invented. Complementary-poor, same-base-rich joints (R2) support “continuation, not delimiter.” The capability is independent of DNA content and of repo paths.
- **Cons:** TT/AA at joints may just be the global AT-rich dimer background sampled every 70 bases, not a seam protocol — v4 listed joints in isolation, so this mapping is still untested against the whole tape. Joining with a space is a prose convenience the DNA does not have (FASTA concatenates with no gap). Island geography is unused by the unwrapper. Unwrap is useful but a thin, well-known algorithm.
- **Report builder changes:** Replaced island tables and joint-count lists with a **joint vs global dimer contrast**: overlapping dinucleotides on the linear tape versus dinucleotides only at wrap joints, with enrichment (joint-share / global-share), same-base share in both samples, and the most enriched/depleted dimers. Islands, complementary-joint %, and homopolymers shrink to a remainder line. This is a different reading (two sampling frames of the same 16-mer alphabet) so the next hypothesis can keep or abandon wrap-as-protocol based on whether joints are actually special.

## Iteration #5
- **Hypothesis:** The DNA encodes a *rare-class island protocol* for arbitrary text, not a wrap continuation, not a grep tape, and not a banner splitter. Concrete signals from the v5 joint-vs-global dimer report: (R1) same-base dimers are **35.9% globally vs 36.1% at wrap joints**, and the most enriched joint dimer is `GA` × **1.08** (most depleted `CC` × 0.87) — wrap seams are not a special protocol, so wrap-as-display is abandoned; (R2) GC is the unused minority mass, **24.14%** (G 63258 / C 65049 of 531490); (R3) single-base homopolymers of G and C max out at 7 while A×22 / T×18, so the rare class is not a long banner but short mixed islands that were never counted. Therefore the useful system is a **rare-class island scanner**: the caller pastes a log, dump, or draft; the app takes symbols from the rarest upward until they cover ~24.14% of non-whitespace mass (skipping any symbol that itself exceeds the AT-like majority floor 75.86%); then lists consecutive runs of that class (hex blobs, IDs, punctuation clusters). Default min-island 3 sits below the measured GC homopolymer max of 7. Payload is caller text; the DNA is only the minority-class rule.
- **Functionality changes:** Shared class `RareClassScanner` (no `FileStorageService`, no `jcvi-dna.txt`). Web: `/rare` form UI; `POST /api/rare`. MCP: `rare_islands`. Both surfaces. Tape, banner split, pair-drift, and unwrap from #1–#4 are kept.
- **Pros:** R1 is a measured reason to abandon wrap-as-protocol rather than a preference. R2 maps onto a real agent need: pulling rare-token islands (hex, IDs, `====` punctuation clusters) out of a pasted log without writing a project file. The 24.14% mass target and majority-break rule are taken from GC/AT shares, not invented. The capability is independent of DNA content and of repo paths.
- **Cons:** “Bottom 24% of a large alphabet” is not the same object as “two rare DNA letters that already form a closed class.” Min-island 3 is a usefulness floor, not a measured mixed-GC length (v5 only had single-base homopolymer maxima). Skipping symbols above 75.86% share is the AT analog, but English and logs rarely have one letter that dominant, so the skip often does nothing. Glueing every equally-rare symbol into one class can merge hex digits with punctuation that happens to share the tail. The scanner is useful but a thin, frequency-ranked highlighter.
- **Report builder changes:** Replaced the joint-vs-global dimer lead with a **two-class AT vs GC island census** on the linear tape: count of GC islands (mixed G/C allowed), longest GC island, buckets ≥5 and ≥10, GC mass inside islands, and the AT-island counterparts. Joint dimer enrichment, wrap widths, skew islands, and homopolymers shrink to a remainder line. This is a different reading (geography of the minority super-letter, not 16-mer sampling at wrap seams) so the next hypothesis can keep or abandon rare-class clustering based on whether mixed GC islands are actually longer than the old G/C homopolymer cap of 7.

## Iteration #6
- **Hypothesis:** The DNA encodes a *rare-break tokenization protocol* for arbitrary text, not a rare-island highlighter and not a wrap protocol. Concrete signals from the v6 AT/GC island report: (R1) mixed GC islands **do not cluster** — longest **9**, **0** of length ≥ 10, while G/C homopolymers already maxed at 7, so the rare class is not payload; (R2) AT islands are the payload — longest **54**, mean length **~4.05** (403183 majority bases / 99495 AT islands); (R3) GC mass stays **24.14%**. Therefore the useful system is a **rare-break tokenizer**: the caller pastes a log or dump; the app takes the bottom ~24.14% of symbol mass as *breaks* (the GC analog) and lists the majority-class tokens between those breaks (the AT analog). Default min-token **2** drops the length-1 crumbs that two-class alternation forces. Whitespace also breaks, the way non-canonical bases skip island accounting. Payload is caller text; the DNA is only the minority-as-delimiter rule. Inverse of iteration #5 (there the rare class was the thing to keep).
- **Functionality changes:** Shared class `RareBreakTokenizer` (reuses `RareClassScanner` for the rare alphabet; no `FileStorageService`, no `jcvi-dna.txt`). Web: `/tokens` form UI; `POST /api/tokens`. MCP: `cut_tokens`. Both surfaces. Tape, banner split, pair-drift, unwrap, and rare islands from #1–#5 are kept.
- **Pros:** R1 is a measured reason to abandon rare-as-payload: GC never reaches length 10 even when G and C may mix. R2 maps onto a real agent need: splitting pasted logs into tokens on empirically rare punctuation/digits of *that* paste, without a hardcoded `\\W` class and without writing a project file. The 24.14% break class and min-token 2 are taken from GC share and AT-island crumbs, not invented. The capability is independent of DNA content and of repo paths.
- **Cons:** Two-class island *counts* (99494 vs 99495) always differ by at most 1, so alternation is tautological — only the *length* asymmetry carries the delimiter claim. Mapping “bottom 24% of a large alphabet” onto “punctuation” is analogical; in English the rare tail may be digits and odd letters, not breaks. Whitespace-as-break is a usefulness choice the DNA does not have. Min-token 2 sits below the measured AT mean of ~4. The tokenizer is useful but a thin, frequency-ranked split; it does not stem, dehyphenate, or respect quotes.
- **Report builder changes:** Replaced the AT/GC island lead with a **codon-frame (period-3) census**: non-overlapping triplets in start phases 0/1/2, ATG and TAA/TAG/TGA counts, GC% at codon positions 1/2/3, GC spread |pos3−pos1|, and the top codon per phase. Island counts, wrap dimers, and homopolymers shrink to a remainder line. This is a different reading (3-periodic coding-like structure, not two-class runs) so the next hypothesis can keep or abandon tokenization based on whether one phase actually looks coding-like.

## Iteration #7
- **Hypothesis:** The DNA encodes a *phase-invariant k-mer stamp protocol* for arbitrary text, not a coding ORF and not a rare-break tokenizer. Concrete signals from the v7 codon-frame report: (R1) GC% by codon position is flat — max spread **1.15** across phases; (R2) the top triplet is **`TTT` in every phase** (×12522 / ×12455 / ×12834), so the mode 3-mer does not depend on reading frame; (R3) ATG peaks in phase **1** (2837) while stops peak in phase **2** (17133) — there is no single ORF. Therefore the useful system is a **k-mer stamp ranker**: the caller pastes a log or dump; the app folds case, drops whitespace (linear-tape analog), counts *overlapping* k-mers, and lists the most common stamps (log prefixes, boilerplate, copy-paste fragments). Default **k=3** is the measured codon width that failed to privilege a phase. Inverse of iteration #5 (there the rare class was the find; here the *mode* k-mer is). Payload is caller text; the DNA is only the phase-invariant mode rule.
- **Functionality changes:** Shared class `KmerStamp` (no `FileStorageService`, no `jcvi-dna.txt`). Web: `/stamps` form UI; `POST /api/stamps`. MCP: `kmer_stamps`. Both surfaces. Tape, banner split, pair-drift, unwrap, rare islands, and rare-break tokens from #1–#6 are kept.
- **Pros:** R1+R2 are a measured reason to abandon coding/period-3 as the product: the same 3-mer wins every frame. Ranking overlapping 3-grams is a real agent need (find repeated log stamps without being told the motif and without writing a project file). k=3 is taken from the census width, not invented. The capability is independent of DNA content and of repo paths.
- **Cons:** `TTT` winning all frames may just be AT-rich homopolymer background (T=38.26%) leaking into every phase, not a stamp protocol. Dropping whitespace glues adjacent words (`the cat` → `THECAT`), which the DNA does not have. MIN_COUNT=2 and MAX_STAMPS=20 are usefulness caps. Overlapping k-mers on a large alphabet explode combinatorially; the tool is a thin frequency table, not a phrase chunker. Mapping DNA `TTT` onto log prefixes is analogical.
- **Report builder changes:** Replaced the codon-frame lead with a **same-base lag census**: match rate of tape[i]==tape[i+lag] at lags 1, 2, 3, 10, and 70 versus independence sum p_b², plus peak lag and enrichment. Codon ATG/stops, GC islands, and wrap dimers shrink to a remainder line. This is a different reading (identity as a function of distance, not 64-mer bags in three phases) so the next hypothesis can keep or abandon k-mer stamps based on whether lag 1 actually outruns lag 3 and lag 70.

## Iteration #8
- **Hypothesis:** The DNA encodes a *fold / palindrome protocol* for arbitrary text, not a forward-lag k-mer stamp ranker. Concrete signals from the v8 same-base lag report: (R1) the tape is nearly memoryless — peak lag **1** match **35.95%**, enrichment only **×1.134** vs independence Σp² = **0.3169**; lag 10 × **0.993** and wrap lag 70 × **0.988**, so k-mer stamps are mostly letter frequency; (R2) lag **2** is *depleted* (**29.91%**, × **0.944**), which discourages odd XYX 3-palindromes; (R3) Chargaff A=199831 ≈ T=203352 is unused by forward identity — pairing is a *fold*, not a lag. Therefore the useful system is an **even palindrome finder**: the caller pastes text; the app folds case, strips whitespace (linear-tape analog), and lists even palindromes of length ≥ **4** that are not homopolymers (the lag-1 bump already covered by stamps). Default min 4 is the first even length above the depleted lag-2 slot. Payload is caller text; the DNA is only the fold-not-lag rule. Inverse of iteration #7 (there identity was a forward stamp).
- **Functionality changes:** Shared class `PalindromeScan` (no `FileStorageService`, no `jcvi-dna.txt`). Web: `/fold` form UI; `POST /api/fold`. MCP: `find_palindromes`. Both surfaces. Tape, banner split, pair-drift, unwrap, rare islands, rare-break tokens, and k-mer stamps from #1–#7 are kept.
- **Pros:** R1 is a measured reason to abandon stamps-as-protocol: lags other than 1 sit at ~1.0 enrichment. Finding mirrored spans in a paste (ABBA-style tokens, palindromic IDs, case-folded mirrored punctuation) is a real agent need without writing a project file. Min 4 and skip-homopolymer follow lag-2 depletion and lag-1 already being stamps. The capability is independent of DNA content and of repo paths.
- **Cons:** Text palindrome (reverse equality) ≠ DNA reverse-complement; the product does not implement A↔T pairing. Min 4 from lag-2 depletion is a stretch — lag 2 is any X.X, not specifically a palindrome. Skipping homopolymers abandons the actual peak lag. MAX_HITS=40 and MAX_RADIUS=40 are usefulness caps. The finder is a thin classic expand-around-center algorithm, not a hairpin/gap matcher.
- **Report builder changes:** Replaced the same-base lag lead with a **foldback stem census**: reverse-complement palindromes (A↔T, G↔C around even and odd centers) of length ≥ 4, longest RC stem, AT vs GC pair contacts inside stems, versus even same-base palindromes that are not homopolymers. Lags, codon frames, and islands shrink to a remainder line. This is a different reading (pairing as a fold around a center, not identity as a function of forward lag) so the next hypothesis can keep or abandon palindrome-as-protocol based on whether RC stems are actually longer or more numerous than letter palindromes.

## Iteration #9
- **Hypothesis:** The DNA encodes a *stem-loop / enclosure protocol* for arbitrary text, not a solid palindrome finder. Concrete signals from the v9 foldback report: (R1) reverse-complement stems **beat** same-base palindromes — longest **34 vs 24**, count **96208 vs 40569** even same-base — so pairing (A↔T, G↔C) is the fold, not reverse equality; (R2) odd RC **51553 > even 44655**, so the center is typically unpaired (a 1-base loop); (R3) AT pairs inside RC stems **216595 vs GC 21233**, the abundant complementary class. Therefore the useful system is a **complementary span extractor**: the caller pastes code, JSON, XML, or a log; the app nest-matches `()[]{}<>` (the complementary analog, not quotes — quotes are same-base folds, which lost) and lists the enclosed loops. Default min loop **1** is the unpaired-center analog. Payload is caller text; the DNA is only the pair-around-a-gap rule. Inverse of iteration #8 (there the fold was a solid even palindrome) and distinct from #3 (there pairing was a windowed *imbalance* tally, not a nest-match that extracts the interior).
- **Functionality changes:** Shared class `StemLoop` (no `FileStorageService`, no `jcvi-dna.txt`). Web: `/loop` form UI; `POST /api/loop`. MCP: `extract_spans`. Both surfaces. Tape, banner split, pair-drift, unwrap, rare islands, rare-break tokens, k-mer stamps, and palindrome fold from #1–#8 are kept.
- **Pros:** R1 is a measured reason to abandon letter palindromes: RC is longer and more numerous. Nest-matching complementary delimiters and returning the enclosed payload is a real agent need (pull a JSON value, a function argument, an XML/HTML tag body from a paste without writing a project file). Min loop 1 and skip-quotes follow odd>even and RC>same-base, not preference. Distinct from pair-drift: this extracts matched interiors instead of scoring window skew. The capability is independent of DNA content and of repo paths.
- **Cons:** Mapping A↔T/G↔C onto `()[]{}<>` is still analogical — the DNA has no brackets (#3 had the same stretch). Skipping quotes because they are “same-base” fights how English and code actually enclose strings. MAX_HITS=40 is a usefulness cap. The matcher is a thin stack algorithm, not a parser (it does not understand quotes, escapes, or languages). Odd>even only justifies loop=1, not nested XML-sized payloads.
- **Report builder changes:** Replaced the adjacent foldback-stem lead with a **gapped hairpin census**: reverse-complement stems of paired length ≥ 4 counted separately at loop widths 0, 1, 2, 3, 5, 8, and 13, plus modal loop, adjacent vs gapped totals, and longest stem in each class. Foldback even/odd counts shrink to a remainder line. This is a different reading (loop width as the variable, not stem-or-not around an immediate center) so the next hypothesis can keep or abandon enclosure based on whether some loop > 0 actually outruns a solid (loop 0) palindrome.

## Iteration #10
- **Hypothesis:** The DNA encodes a *mismatch-tolerant motif protocol* for arbitrary text, not an exact enclosure / stem-loop. Concrete signals from the v10 hairpin-loop report: (R1) exact complementary stems are **flat across loop widths** — 44655 / 51553 / 52956 / 52464 / **54503** / 53174 / 54443 at loops 0, 1, 2, 3, 5, 8, 13, so a preferred gap is not a protocol; (R2) the longest stem is still **adjacent loop 0 (34)**, while the modal loop 5 only reaches 26 — extra unpaired bases do not grow pairing; (R3) AT vs GC pair shares stay ~90/10 at every loop, the same global Chargaff background. Therefore the useful system is a **fuzzy finder**: the caller pastes text and a motif; the app case-folds and lists sliding Hamming near-matches. Default max distance **1** is the smallest substitution; min motif **4** is the hairpin MIN_STEM analog. Payload is caller text; the DNA is only the exact-pairing-is-background rule. Inverse of iteration #1 (there find was fold-then-exact) and a replacement of #9 (there pairing had to be exact around a loop).
- **Functionality changes:** Shared class `FuzzyFind` (no `FileStorageService`, no `jcvi-dna.txt`). Web: `/fuzzy` form UI; `POST /api/fuzzy`. MCP: `fuzzy_find`. Both surfaces. Tape, banner split, pair-drift, unwrap, rare islands, tokens, stamps, palindrome fold, and stem loops from #1–#9 are kept.
- **Pros:** R1 is a measured reason to abandon enclosure: every loop width produces ~the same stem count. Typo-tolerant search of a pasted log (ERROR vs ERORR, hello vs hallo) is a real agent need without writing a project file, and it is not a restatement of exact `tape_find`. Min motif 4 and max distance 1 are taken from MIN_STEM and the smallest mismatch, not invented. The capability is independent of DNA content and of repo paths.
- **Cons:** Hamming substitutions are not DNA reverse-complement mismatches — mapping complementary-pair errors onto letter typos is analogical. Insertions/deletions are ignored (EROR vs ERROR of different length will miss). Min motif 4 is awkward for short English words. MAX_HITS=40 is a usefulness cap. The tool is a thin sliding window, not an aligner.
- **Report builder changes:** Replaced the gapped-hairpin-by-loop lead with a **fixed-window pairing-mismatch census**: Hamming distance 0–4 of each 4-mer versus the reverse-complement of the adjacent 4-mer, versus binomial expectation from complementary-pair chance 2pA pT + 2pG pC, plus modal distance and distance-0 enrichment. Hairpin loop counts shrink to a remainder line. This is a different reading (mismatch distance as the variable, not loop width of exact stems) so the next hypothesis can keep or abandon fuzzy search based on whether distance 0 is actually enriched or the histogram is just binomial.

## Spec change (not an iteration): log-analysis loop

Pros/cons of a hypothesis as a log-analysis system are no longer speculative. Algorithms
must emit DEBUG logs (`if (log.isDebugEnabled()) { log.debug(...); }`). Before pros/cons
the full test suite writes `reports/logs/test.log`; the log-analysis facade then writes
`reports/logs/report.json`. The agent must read that JSON and ground Pros/Cons in it.
See `docs/tz.md` §5.6–5.7 and §6.7–6.9. This is infrastructure, not Iteration #11.

## Iteration #11
- **Hypothesis:** The DNA encodes an *adjacent-block contrast / stutter protocol* for arbitrary text, not a mismatch-tolerant motif search. Concrete signals from the v11 pairing-mismatch report: (R1) exact reverse-complement pairing is **depleted** — distance 0 share **0.0085** vs expected **0.0101** (× **0.846**); (R2) the mode is Hamming **3** of 4, and distance 1 is also depleted (× **0.899**), so one-substitution fuzzy search is not the peak; (R3) distance **4** is the **most enriched** (× **1.099**) — neighbors systematically differ. Therefore the useful system is a **stutter scanner**: the caller pastes a log or dump; the app walks overlapping windows of width **4** (the measured pair size) and Hamming-compares each block to the next; hits are distances ≤ **1** (the depleted class). Payload is caller text; the DNA is only the neighbors-should-differ rule. Inverse of iteration #10 (there a motif may almost match anywhere) and distinct from #7 (there frequency is global, not adjacent).
- **Functionality changes:** Shared class `BlockContrast` (no `FileStorageService`, no `jcvi-dna.txt`). Web: `/contrast` form UI; `POST /api/contrast`. MCP: `block_contrast`. Log-analysis facade gains a `contrast` JSON section (web + MCP `analyze_logs`). Tape through fuzzy from #1–#10 are kept.
- **Pros:** R1–R3 are a measured reason to abandon fuzzy-as-protocol: distance 0/1 are below chance and the mode is 3. Adjacent-stutter detection is a real log need (repeated tokens, copy-paste fragments) without writing a project file. Grounded in `reports/logs/report.json` after the test journal: `contrast.modalDistance=4`, `meanDistance≈3.81`, `stutterCount=401` of `scanned=75602` (~0.53%) at `flagMax=1`, `truncated=false` — the app's own DEBUG log is high-contrast adjacent 4-mers with a thin stutter tail, matching DNA's depleted-low / enriched-max shape. Width 4 and flag ≤1 are taken from the census pair size and depleted distances, not invented. The capability is independent of DNA content and of repo paths.
- **Cons:** Mapping RC-anti-pairing onto *identity* Hamming is analogical — the DNA compared left to reverse-complement(right), not to right. Width 4 is short for English log lines, so some of the 401 journal stutters may be overlapping DEBUG punctuation rather than true duplicated records. `MAX_HITS=40` caps the hit list while `stutterCount` can be larger (401). Other facade sections still saturate caps (`tape.runCount=40`, `drift.hotspotCount=80`, `rare.islandCount=80`, `tokens.tokenCount=80`, `palindromes.hitCount=40`, `spans.spanCount=40`, `fuzzy.hitCount=40`) and banners stay at `sectionCount=1`, so contrast is the first section whose *mode* actually matches the DNA claim. The scanner is a thin sliding Hamming, not a line-oriented duplicate detector or an aligner.
- **Report builder changes:** Replaced the RC-only pairing-mismatch histogram with a **three-map neighbor Hamming census**: identity, reverse, and reverse-complement of adjacent 4-mers, each with modal distance and distance-0 enrichment versus Σp² or Chargaff pair chance. The v11 RC histogram shrinks to a remainder line. This is a different reading (which neighbor *map* is anti-matched, not which Hamming *distance* of RC) so the next hypothesis can keep or abandon identity stutter-scan based on whether identity distance 0 is also depleted or only RC is.

## Iteration #12
- **Hypothesis:** The DNA encodes a *mirror-joint / reverse-neighbor protocol* for arbitrary text, not an identity stutter-scan. Concrete signals from the v12 neighbor Hamming report: (R1) reverse distance-0 is **enriched** — share **0.0114** vs expected **0.0101** (× **1.130**); (R2) identity distance-0 is **depleted** (× **0.891**), so adjacent copies are not the protocol; (R3) RC distance-0 is **depleted** (× **0.846**), so complementary pairing is also not the protocol. Therefore the useful system is a **mirror-joint scanner**: the caller pastes text; the app walks overlapping windows of width **4** (the measured pair size) and flags the next block when it is the reverse of the current one *and* not a copy (reverse Hamming 0, identity Hamming > 0). Inverse of iteration #11 (there identity-low was the hit) and distinct from #8 (there palindromes expand around a center at any even length ≥ 4, skipping homopolymers). Payload is caller text; the DNA is only the reverse-seam rule.
- **Functionality changes:** Shared class `MirrorJoint` (no `FileStorageService`, no `jcvi-dna.txt`). Web: `/mirror` form UI; `POST /api/mirror`. MCP: `find_mirrors`. Log-analysis facade gains a `mirrors` JSON section (web + MCP `analyze_logs`). Tape through contrast from #1–#11 are kept. Module split (TZ §6.14) is **not** indicated: still a single Gradle module.
- **Pros:** R1–R3 are a measured reason to abandon stutter-scan as the DNA protocol: only the reverse map is enriched at distance 0. Finding reversed adjacent tokens in a paste (mirrored IDs, `abcddcba`-style joints) is a real need without writing a project file, and excluding identity copies keeps `AAAA|AAAA` from counting as a mirror. Grounded in `reports/logs/report.json` after the test journal: `truncated=false`, `inputLength=82516`, `contrast.modalDistance=4` / `meanDistance≈3.80` / `stutterCount=419` of `scanned=82509` still matches DNA's neighbors-should-differ background, while `mirrors.width=4` ran on the same `scanned=82509` windows — the scanner executed on the journal, not on DNA. Width 4 and the reverse-0 / identity>0 rule are taken from the census, not invented. The capability is independent of DNA content and of repo paths.
- **Cons:** The same JSON falsifies reverse-joints as a *log-analysis* protocol: `mirrors.jointCount=0`. The app's DEBUG journal has no adjacent reverse 4-mers that are not copies, so the DNA reverse enrichment (×1.130) does not transfer to this text. `palindromes.hitCount=3` / `longest=4` on the same journal shows even letter palindromes are already rare; requiring the reverse of the *next* block is stricter still. Mapping DNA reverse onto case-folded English is analogical — log tokens rarely read as reverse neighbors. Other facade sections still saturate caps (`tape.runCount=40`, `drift.hotspotCount=80`, `rare.islandCount=80`, `tokens.tokenCount=80`, `spans.spanCount=40`, `fuzzy.hitCount=40`) and `banners.sectionCount=1`. The scanner is a thin sliding reverse Hamming, not a wrap-aware seam detector.
- **Report builder changes:** Replaced the three-map neighbor Hamming table with a **wrap vs interior reverse census**: reverse-0 share of adjacent 4-mers at FASTA wrap joints (last 4 of line N vs reverse of first 4 of line N+1) versus the same measurement on the linear interior tape, plus wrap/interior ratio. The v12 3-map table shrinks to a remainder line. This is a different reading (geography of the reverse enrichment, not which neighbor *map* is enriched) so the next hypothesis can keep or abandon linear mirror-scan based on whether reverse-0 actually concentrates on wrap seams (TT/AA joints are palindromic) or is uniform along the tape.

## Iteration #13
- **Hypothesis:** The DNA encodes a *wrap-seam anti-mirror protocol* for arbitrary text, not a linear reverse-joint scanner. Concrete signals from the v13 wrap-vs-interior reverse report: (R1) wrap reverse-0 share is **0.0104** (79 of 7592 joints) vs interior **0.0114** (6059 of 531483) — wrap/interior **0.913**, so palindromic glue is *depleted* at display wraps, not enriched; (R2) wrap is therefore not the home of the v12 reverse bump, and linear overlapping reverse-scan (#12) already found `mirrors.jointCount=0` in logs because it ignores newlines; (R3) modal wrap remains **70**, block size **4**. Therefore the useful system is a **seam guard**: the caller pastes hard-wrapped text; the app inspects newline joints of lines ≥ **70** characters and flags the last **4** vs reverse(first 4) when that reverse matches and the blocks are not copies. Hits are the depleted wrap-anomaly class. Inverse of #12 (there reverse joints anywhere were payload) and distinct from #4 (there every 70-line is joined; this flags palindromic glue without unwrapping). Payload is caller text; the DNA is only the wrap-should-not-mirror rule.
- **Functionality changes:** Shared class `SeamGuard` (no `FileStorageService`, no `jcvi-dna.txt`). Web: `/seam` form UI; `POST /api/seam`. MCP: `flag_seams`. Log-analysis facade gains a `seams` JSON section (web + MCP `analyze_logs`). Tape through mirrors from #1–#12 are kept. Module split (TZ §6.14) is **not** indicated: still a single Gradle module.
- **Pros:** R1 is a measured reason to abandon wrap-as-mirror-payload: reverse-0 is poorer at FASTA joints than on the linear tape. The product samples *newlines*, which #12's linear scanner does not. Grounded in `reports/logs/report.json` after the test journal: `truncated=false`, `inputLength=88651`, `reflow.sourceLines=692` / `stitches=691` / `paragraphCount=1` — the journal *is* hard-wrapped — and `seams.scanned=691` with `wrapWidth=70` / `blockWidth=4` inspected those wrap joints (not DNA). `mirrors.jointCount=0` on the same `scanned=88644` overlapping windows shows why a line-aware seam pass was needed. `hitCount=0` of 691 matches the DNA depletion claim: palindromic wrap glue is the avoided class, and this journal has none. Width 70 and block 4 are taken from the census, not invented. The capability is independent of DNA content and of repo paths.
- **Cons:** The same JSON shows the tool extracts no actionable seams: `seams.hitCount=0`. As log analysis it reports "wraps are clean" rather than listing anomalies an agent would fix. DNA wrap reverse-0 is 1.04% (about 7 expected in 691 joints); the journal is even emptier, so the mapping from DNA reverse onto English line prefixes/suffixes is analogical and possibly DNA-specific. Other facade sections still saturate caps (`tape.runCount=40`, `drift.hotspotCount=80`, `rare.islandCount=80`, `tokens.tokenCount=80`, `palindromes.hitCount=40`, `spans.spanCount=40`, `fuzzy.hitCount=40`) and `banners.sectionCount=1`. The guard is a thin two-line Hamming, not a wrap-quality linter that knows tokens or hyphenation.
- **Report builder changes:** Replaced the wrap-vs-interior two-sample table with a **reverse-0 phase census**: share of reverse-0 adjacent 4-mers binned by start offset modulo wrap width 70, plus peak phase, wrap-column (width−4) share, and wrap/mean ratio. The v13 wrap/interior ratio shrinks to a remainder line. This is a different reading (which *column* of the wrap frame holds reverse enrichment, not wrap-sample vs interior-sample) so the next hypothesis can keep or abandon seam-guard based on whether reverse actually dips at the wrap column or peaks at some other phase.

## Iteration #14

Concrete signals from the v14 reverse-phase report: (R1) reverse-0 **peaks at phase 19** (share **0.0140** vs mean **0.0114**, × **1.228**), neither column 0 nor the wrap column; (R2) wrap phase **66** share **0.0104** (wrap/mean **0.913**) confirms palindromic glue at the display seam is depleted, so seam-guard was sampling the wrong column; (R3) modal wrap remains **70**, block **4**. Therefore the useful system is a **phase-joint scanner**: the caller pastes text; the app drops newlines (FASTA-concat analog), walks frames of width **70**, and at column **19** flags when the next 4 characters are the reverse of the current 4 and not a copy. Inverse of #13 (there wrap-column reverse was the anomaly) and distinct from #12 (there every overlapping offset was a candidate). Payload is caller text; the DNA is only the peak-column reverse-field rule.
- **Functionality changes:** Shared class `PhaseJoint` (no `FileStorageService`, no `jcvi-dna.txt`). Web: `/phase` form UI; `POST /api/phase`. MCP: `phase_mirrors`. - **Pros:** R1–R2 are a measured reason to abandon seam-guard as the DNA protocol: reverse lives at column 19, not at wrap 66. That sample is denser than `seams.scanned=734` and narrower than `mirrors.scanned=94867` (`jointCount` still 0). Width 70, phase 19, and block 4 are taken from the census, not invented. The capability is independent of DNA content and of repo paths.
- **Cons:** The same JSON falsifies reverse-at-column-19 as a *log-analysis* protocol: `phase.hitCount=0`. The scanner is a thin strided Hamming, not a fixed-width record parser.

The v14 reverse-only peak (column 19) shrinks to a remainder line. This is a different reading (which *map* owns the peak column, not which *column* owns reverse) so the next hypothesis can keep or abandon a reverse field at 19 based on whether identity and RC peak elsewhere or all three share the same compositional column.

## Iteration #15
- **Hypothesis:** The DNA encodes a *three-slot wrap-frame record protocol* for arbitrary text, not a single reverse field at column 19. Concrete signals from the v15 map-phase report: (R1) identity, reverse, and RC peak at **three different columns** — identity **58** (share **0.0121**), reverse **19** (**0.0140**), RC **4** (**0.0111**) — so reverse-at-19 is not a compositional artifact of one shared phase; (R2) #14's Hamming hit-test at 19 found `phase.hitCount=0` in logs, which is the wrong readout if those columns are *fields* to extract rather than reverse joints to flag; (R3) modal wrap remains **70**, and the census windows were adjacent 4-mers, so each field is an 8-character slot (two adjacent 4-mers). Therefore the useful system is a **frame-field extractor**: the caller pastes text; the app drops newlines, splits into frames of width **70**, and pulls the 8-character slots at columns **4 (RC), 19 (reverse), and 58 (identity)**, ranking the mode of each. Inverse of #14 (there only reverse Hamming at 19 was a hit) and distinct from #7 (there stamps were global overlapping 3-mers, not column-aligned). Payload is caller text; the DNA is only the three-column record layout.
- **Functionality changes:** Shared class `FrameFields` (no `FileStorageService`, no `jcvi-dna.txt`). Web: `/fields` form UI; `POST /api/fields`. MCP: `extract_fields`. Log-analysis facade gains a `fields` JSON section (web + MCP `analyze_logs`). Tape through phase from #1–#14 are kept. Module split (TZ §6.14) is **not** indicated: still a single Gradle module.
- **Pros:** R1 is a measured reason to abandon a single reverse field: the three maps own three columns, so the wrap frame is a typed record. Grounded in `reports/logs/report.json` after the test journal: `truncated=false`, `inputLength=101023`, `fields.scanned=1420` / `recordCount=1420` / `wrapWidth=70` with **three different modes** — `topRc="09-12 14"` (a timestamp fragment), `topReverse=".WEBJCVI"` (a logger-name fragment), `topIdentity=" ORG.WEB"` (a package prefix). Extraction succeeds on the same stride where `phase.hitCount=0` of `phase.scanned=1421` found no reverse joints. Width 70 and columns 4/19/58 are taken from the census, not invented. The capability is independent of DNA content and of repo paths.
- **Cons:** Mapping DNA RC/reverse/identity geography onto timestamp / logger / package columns is analogical — Logback layout, not a reverse-complement alphabet, produced those three modes. Dropping newlines to mimic FASTA concat still mis-aligns DEBUG lines that are not 70-character records (`reflow.sourceLines=777` / `paragraphCount=1`). `MAX_RECORDS=40` caps the listed rows while `recordCount` can be 1420. The extractor is a thin strided substring, not a record parser that knows field names or delimiters.
- **Report builder changes:** Replaced the three-map phase table with a **slot composition census**: GC% and the mode 8-mer of the three wrap-frame slots at columns 4, 19, and 58. The v15 map-phase peaks shrink to a remainder line. This is a different reading (what *lives inside* the three peak columns, not which *map* peaks where) so the next hypothesis can keep or abandon typed fields based on whether the slots actually differ in GC% / alphabet or are the same AT background sampled three times.

## Iteration #16
